**The 60% self-contained figure is the headline finding.** The test plan assumed
self-contained examples would be a useful minority; they're the majority. That's
**852 examples that are directly runnable with no `StormEvents` fixture, no
sample database, and no external data** — they carry their own input. The
acceptance corpus is substantially cheaper to stand up than planned.

## The decisive number — closure coverage

A doc example is only usable as a test if **every** operator in it is supported.
So the useful metric isn't per-operator frequency, it's *closure* coverage:

| Implemented through | Blocks fully covered | % of all | Self-contained covered | % of self-contained |
|---|---|---|---|---|
| **Wave 1** | **1,068** | **75%** | **671** | **79%** |
| Wave 2 | 1,158 | 81% | 737 | 87% |
| Wave 3 | 1,232 | 86% | 780 | 92% |

**Wave 1 alone unlocks three quarters of the corpus.** That is a strong argument
for shipping a narrow MVP and resisting scope creep — Waves 2 and 3 together add
only 11 more percentage points.

### Three surprises worth acting on

1. **`render` is the 5th most common operator (96 blocks) and is worthless to
   us.** It's a client-side *visualization* directive — Kusto returns the same
   rows either way. We return relations, not charts. **Recommendation: parse and
   ignore it (a no-op that preserves the input relation), rather than raising
   `KqlUnsupportedError`.** Treating it as unsupported would needlessly disqualify
   ~7% of the corpus. This is a real decision the scan surfaced.
2. **The graph family is bigger than expected** — `graph-match` (57),
   `make-graph` (33), plus `graph-shortest-paths`, `graph-to-table`,
   `graph-mark-components` ≈ **100 blocks**. It is an entire subsystem with no
   DuckDB analogue. **Recommendation: defer explicitly** and say so in the
   coverage matrix, so the gap is visible rather than a silent hole.
3. **`evaluate` (70 blocks) is plugin dispatch**, not one operator — `bag_unpack`,
   `pivot`, `narrow`, etc. It should be scoped as its own family in Wave 3, not
   treated as a single mapping.

### Long-tail Wave-1 operators
Several planned Wave-1 operators are barely exercised in the docs — `distinct`
(4), `project-rename` (4), `project-reorder` (3), `limit` (2), `project-keep` (1),
`externaldata` (0). They stay in Wave 1 (they're trivial and users expect them),
but **the docs corpus will not test them meaningfully** — they need hand-authored
cases. Frequency alone would under-rank them; that's a known limitation of this
signal.

**Method caveat:** the function counter matches `identifier(`, so it picks up
type names in `datatable` schemas (`real`, `int`), join kinds (`inner`), and
graph clauses (`match`, `graph`, `labels`). Treat the function table as
*indicative*, not exact. The operator table is much cleaner.

approximate (R11), so the approximation policy needs settling sooner than its
low raw count suggests.

## What this changes

1. **Wave 1 is validated and should stay narrow.** 75% closure coverage from the
   planned set; the marginal value of widening it is low.
2. **Add `render` as an explicit no-op** to Wave 1. Cheap, and worth ~7% of the
   corpus.
3. **Defer the graph family explicitly**, as a named gap in the coverage matrix.
4. **Split `evaluate` into per-plugin mappings** rather than one entry.
5. **The self-contained corpus (852 blocks) is the primary acceptance suite.**
   Sample-DB fixtures (`StormEvents` et al.) become a second-phase concern, which
   also defers the fixture-hosting open question.
6. **Hand-author cases for the long tail** — `distinct`, `project-rename`,
   `limit`, `project-keep` will not be covered by harvested examples.
