## 1. The suppression ledger — real, and the tool was measuring it wrong

**Tier:** Safe (delete) / Careful (widen `select`).

**Evidence.** `metrics.md` and the playbook both claimed *"all 125 `# noqa`
directives... ruff reports as unused."* That claim came from
`tools/maintenance_metrics.py`, which shelled out to `ruff check --select
RUF100`. On the ruff CLI `--select` **replaces** the configured rule set for that
invocation; `--extend-select` adds to it. So the check ran with only `RUF100`
enabled, and every rule any directive named looked unselected.

Re-run correctly (`ruff check --extend-select RUF100 src tools tests demo`), the
number is **113, not 125**. Twelve directives are load-bearing under the real
config — `B017`×7, `E402`×4, `E731`×1 — confirmed by stripping the comment and
re-running plain `ruff check` (e.g. `tests/test_databases.py:69`, where
`pytest.raises(Exception)` genuinely trips `B017`).

Of the true 113: **8 are stale-but-harmless** (`E402` in `tools/check_profile.py`,
`harvest_docs.py`, `make_fixtures.py`, `regen_expectations.py` — the rule is
enabled but never fires there, because a `sys.path.insert(...)` shim is E402's
documented exception). The remaining **105 suppress a rule this project has never
enabled**: `PLC0415` (73), `BLE001` (21), `S603` (4), `N802` (4), `S101`,
`RUF012`, `PERF203`. `git log -p -- pyproject.toml` shows `select` has been
exactly `["E","F","I","UP","B"]` since the file's first commit — this was never
narrowed; the noqa convention simply never matched it. Of the 73 `PLC0415`
directives, **69 carry no reason at all**.

**Costs.** 105 comments look like enforced discipline and enforce nothing. A
reviewer who reads `# noqa: BLE001 - any engine failure is the answer` as
"checked and suppressed" is trusting a comment, not a gate — and the two metrics
built to catch exactly this were themselves overcounting.

**Trigger.** The next touch to the ruff config, or the next PR that adds a
directive.

**Exit.** `ruff check --extend-select RUF100 src tools tests demo` reports 0.

**Refactoring.** Two independent commits.
- *(Done.)* Fix the measurement: `--select RUF100` → `--extend-select RUF100`.
- *(Open.)* Fix the ledger, per the playbook's two honest resolutions: delete the
  105 dead directives with `ruff --fix`, folding their reasons into the
  surrounding comment; **or** add `PLC0415`/`BLE001`/`S`/`N`/`PERF`/`RUF` to
  `select` and take the real findings that surface. The second is Careful and is
  its own separately-reviewed change.

## 2. Eight special forms hand-coded beside the registry that exists for them

**Tier:** Careful.

**Evidence.** `render_expr` (`translate/__init__.py:173`) is the branchiest
function in the repo (45 branches) in the top hotspot (17 commits × 2,345 lines).
Inside its `FunctionCall` arm, eight KQL functions are matched by bespoke
`if node.name.lower() == "...":` checks written straight into the dispatcher —
`bin`/`floor` (:257), `tostring` (:263), `reverse` (:265), `pack_array` (:282),
`hash_md5`/`hash_sha1`/`hash_sha256` (:286), `array_concat` (:295), `todatetime`
(:304), `totimespan`/`timespan` (:311) — sitting *around* the
`_SPECIAL_FORMS.get(...)` lookup at :279 that already holds `case`, `strcat`,
`substring`, `round`, `countof`, `zip`, `make_datetime`, `make_timespan`,
`datetime_add/diff/part`, `extract_all` and the eight `startof*`/`endof*`
functions.

Each of the eight has a real reason it cannot be a plain template row in
`functions.py` — `tostring` dispatches on the *runtime* type via `typeof()`,
which a static template cannot express (`render_kql_tostring`, :2854). So the fix
is **not** to move them into `functions.py`: that module cannot call
`render_expr` recursively without a circular import, which is precisely why
`_render_case`, `_render_strcat` and friends live in `translate/__init__.py`. The
fix is to fold the eight into the `_SPECIAL_FORMS` mechanism that is already
there.

**Costs.** Every scalar-function wave (this file has had 17 commits) re-learns
which of two dispatch mechanisms a "needs Python, not a template" function should
join, and a reviewer must read both to know the full special-cased set.

**Trigger.** The next scalar-function mapping needing runtime-type dispatch — the
next `tostring`/`reverse`-shaped function. Not speculatively (M6).

**Exit.** `_SPECIAL_FORMS.get(node.name.lower())` is consulted once, before the
generic `lookup()` fallback, and is the only place special-cased names live;
`render_expr`'s branch count drops by roughly the eight arms removed; the SQL
snapshot is byte-identical.

**Refactoring.** "Turn a special form into a registry row" (Careful tier): for
each, extract the body into a `_render_x(node: ir.FunctionCall)`, register it,
delete the inline `if`. Per the ladder, name the trap each one guards — e.g. the
`hash_*` family's must-go-through-KQL-string-form rule — and point at its
existing test *before* touching it.

> **Amendment, 2026-08-23 (closed).** That mechanic is wrong for **five of the
> eight**, and following it literally would have shipped wrong answers. The five
> are not unconditional dispatch but *guarded arms that fall through*:
> `tostring`, `reverse` and `hash_*` handle one argument and let every other
> arity reach `lookup()` so the arity error names the function; `todatetime` and
> `totimespan` short-circuit only when the argument is already of that type and
> otherwise want the registry's string-parsing template — the common case.
> `_SPECIAL_FORMS` dispatch returned unconditionally, so the move as written
> would have made `todatetime('2024-01-01')` stop parsing strings.
>
> The mechanism now lets a form answer `None` to **decline**. That is a design
> change rather than a move, which is what pushed this from "mechanical" to
> genuinely Careful — and it is the survey's own risk-ladder warning ("two
> branches 'obviously the same' often differ") landing on the survey.

## 3. Five dead registry rows — a template that can never execute

**Tier:** Safe.

**Evidence.** `startofweek`, `endofday`, `endofmonth`, `endofyear` and `endofweek`
are each defined **twice** in `SCALAR_FUNCTIONS` (`functions.py:315-322`, then
again at `:328-344`): once as the `("", (1, 2), ("R8",), "special")` placeholder
its four siblings use, and once with a fully written DuckDB template. The dict
comprehension means the *second* wins — but nothing ever reads it:
`_SPECIAL_FORMS` routes all eight `startof*`/`endof*` names to `_render_period`
(:3239, registered at :3316), and `render_expr` consults `_SPECIAL_FORMS` before
the generic `lookup()`/`.render()` path. `_render_period` builds the SQL itself,
because it has to handle the optional period-offset argument that a template
cannot express.

**Costs.** A contributor "fixing" `endofweek`'s expression — for a leap-second
edge case, say — would edit dead code, watch the tests still pass, and ship
nothing. Silently. That is this project's defining failure mode, aimed at the
registry instead of at the SQL.

**Trigger.** The next change to any `startof*`/`endof*` mapping.

**Exit.** Each of the five has exactly one row, in the placeholder shape its
siblings use; `_render_period` unchanged; `docs/kql-support.md` byte-identical
(it reads `.note`/`.rules`, never `.template`).

**Refactoring.** Delete dead code — remove the five real-template rows at
:328-344, keep the eight placeholders at :315-322.

## 4. Commits are at or over the review ceiling, and it is the steady state

**Tier:** Safe / procedural.

**Evidence.** `median_changed_lines: 285`, `p90: 975`,
`over_review_budget (400): 18/50`. This is not historical drag: the last fifteen
commits alone include four over 900 lines — `e7577b9` (1,123), `2bcdf04` (902),
`aba504d` (898), and the framework commit at HEAD, `6f12ed4` (1,629).

**Costs.** The cheapest number in this report to move, requiring no code change,
and it protects everything above it: the SmartBear/Cisco falloff past 200–400
changed lines bites hardest in a translator whose entire risk model is
"syntactically identical, semantically different".

**Trigger.** Every commit, starting now.

**Exit.** `over_review_budget` trends down over the next 10–20 commits; a feature
and its supporting refactor land as two commits (M1).

**Refactoring.** Not a code transformation — process discipline. Split a feature
commit at its natural seams (grammar / lowering / rendering / tests) instead of
shipping a wave atomically.

## Duplicated emitter branches — looked for, none worth unifying

The nearest-looking pair is `render_join` (`translate/__init__.py:1261`) and
`render_lookup` (:1223). They share a shape — an `ON` predicate via
`render_key_equality`, a projection built from left and right columns — but
differ in exactly the three ways R14 documents and `tests/test_lookup.py` pins:
`lookup` defaults to `leftouter` where `join` defaults to `innerunique` and never
de-duplicates the left key set; `lookup` **drops** the right side's join-key
columns where `join` keeps them and suffixes on collision; `join` alone has
directional semi/anti handling. A naive unification erases all three. Correctly
kept separate, with the reasons stated at the site.
