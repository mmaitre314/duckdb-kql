# Area: Tooling, packaging, CI & docs

**Scope:** `src/duckdb_kql/cli.py`, `__main__.py`, `tools/`, `pyproject.toml`,
`.github/workflows/`, the devcontainer, and the *consistency* of generated docs
(`docs/kql-support.md`, the support matrix, `CHANGELOG.md`, README links).
**Out of scope:** CLI *input safety* (security area) and translation semantics
(translation area) — here the question is whether the build, the tooling, and
the docs tell the truth and stay reproducible.

**Read first:** the [charter](README.md), CONTRIBUTING's "Things CI will check
that are easy to miss" and "Releasing" sections, `docs/cli.md`,
`grammar/UPSTREAM.md`.

The theme of this area is the same charter rule at a different altitude: **a doc
or a build artifact that claims something the code doesn't do is a wrong
answer.** The support matrix that lists a construct the translator refuses, the
`pyproject` that says Layer 0 is dependency-light while an import drags in
duckdb, the CI job that's green because it silently stopped running the check —
these mislead exactly like a bad mapping.

## Generated-artifact consistency (the highest-value checks)

These are the "easy to miss" gates; a review confirms the *code change* and the
*generated output* moved together:

- [ ] **`docs/kql-support.md` regenerates identically.** It's generated by
  `tools/gen_support_matrix.py`; CI fails if stale. A mapping change with no
  matrix change (or a hand-edited matrix) is a defect — the table must not be
  able to claim something the code doesn't do.
- [ ] **The refusal list is honest.** A construct in the `unsupported`/refusal
  set of `gen_support_matrix.py` must actually raise; a construct that's mapped
  must not still be listed as refused. The `Limitations and gotchas` column is
  the point of the doc — check it says what was actually learned from the oracle,
  not a placeholder.
- [ ] **The request-option doc table matches `OPTION_SUPPORT`** (shared with the
  kusto area) — CI checks it; confirm a change kept them in step.
- [ ] **Doc links resolve**, including the absolute ones the README uses for PyPI
  (CI checks this). A new doc or moved file that breaks a link is a finding.

## Packaging (`pyproject.toml`)

- [ ] **The layering claim is enforced, not just stated.** `dependencies` is
  antlr4 only; duckdb/pandas/pyarrow are extras. A new hard dependency added to
  `[project.dependencies]` breaks the Layer-0 promise (cross-check the public-API
  area). CI verifies "Layer 0 installs and works with `duckdb` absent" — confirm
  that job still exercises the claim.
- [ ] **Version triple stays consistent.** `pyproject.toml`, `__init__.py`
  `__version__`, and the git tag must agree; CI fails the release on a mismatch
  (CONTRIBUTING → Releasing). A bump touching only one is a latent release break.
- [ ] **sdist/wheel contents are intentional.** The sdist deliberately *excludes*
  `.claude`, `.github`, `tests/cases`, `tests/fixtures` (the ~29 MB frozen
  corpus). A change that starts shipping fixtures bloats the package; one that
  drops something needed to build/test breaks reproducibility. Verify the
  `exclude`/`packages` lists still match intent.
- [ ] **Tool config is coherent:** `ruff` and `mypy` exclude the vendored
  `_antlr/` (it's regenerated, never edited); the `per-file-ignores` and mypy
  overrides have stated reasons. A new blanket ignore without a reason is a
  finding — the mypy config comment explicitly warns against re-introducing a
  per-module ladder.

## CLI and tooling (`cli.py`, `__main__.py`, `tools/`)

- [ ] **The CLI does not import `duckdb`** (CI checks; also a layering/security
  rule) — build-time translation runs in a minimal image.
- [ ] **Tools are reproducible and single-sourced.** `regen_parser.sh`,
  `regen_expectations.py`, `gen_support_matrix.py`, `make_fixtures.py`,
  `harvest_docs.py` — each should be deterministic and the sole generator of its
  artifact. Two paths that can produce the same file drift apart. Check a tool
  change also updated whatever it generates in the same commit.
- [ ] **The committed parser matches `grammar/Kql.g4`.** The generated parser is
  committed so installs need no Java; CI checks it matches the grammar. A grammar
  edit without a regenerated parser (or vice-versa) is a defect. The ANTLR
  runtime pin in `pyproject.toml` must match the generator version, which is the
  source of record in `tools/regen_parser.sh` (`ANTLR_VERSION`); confirm the two
  still agree, and that `grammar/UPSTREAM.md`'s provenance is current.
- [ ] **CLI exit codes and error output** are appropriate for a build step: a
  refusal or syntax error should exit non-zero with a locatable message, so a
  broken `.kql` fails the build loudly rather than emitting empty/partial SQL.

## CI workflows (`.github/workflows/`)

- [ ] **A green check still runs its check.** Read workflow diffs for a step
  that's been made conditional, `continue-on-error`, or narrowed (a matrix leg
  dropped, a path filter that now skips the job on the changed files). Green
  because it didn't run is the CI equivalent of a weakened test.
- [ ] **The support matrix (3.10 floor / 3.13 ceiling)** is preserved — the mypy
  config depends on running both ends (PEP 695 stubs need 3.12+; 3.10-only code
  must fail on the 3.10 leg). Dropping a Python leg reduces real coverage.
- [ ] **The emulator/oracle job's role is dev-and-CI only** — never a runtime
  dependency, never redistributed, and no timing/perf numbers published from it
  (licence, `docs/licensing.md` §5). A workflow that prints benchmark numbers
  against the emulator is a licensing finding.
- [ ] **Release is tag-builds-but-Release-publishes** (Trusted Publishing, no
  stored token). A change that adds a PyPI token, or makes a tag publish
  directly, weakens the deliberate manual gate.

## Docs prose consistency

- [ ] **`CHANGELOG.md`** has an `Unreleased` entry for a user-visible change,
  and the doctest/examples in `docs/` still match real output (the docs test
  reads `pyproject.toml` and executes examples).
- [ ] **New behaviour is documented where a user looks** (README, getting-started,
  the relevant `docs/` page) — Google's documentation check: update the docs that
  describe building, testing, or interacting with the change.

## What to enumerate as "checked clean"

Which generated artifacts the change should have moved and that they did; that
the version triple, the layering deps, and the sdist excludes are intact; and
that no CI step was silently disabled or narrowed.
