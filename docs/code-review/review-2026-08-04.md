# duckdb-kql — in-depth code review

**Date:** 2026-08-04 · **Reviewed at:** `728fb55` · **Method:** one reviewer per
area, each working its checklist in [`docs/code-review/`](README.md).

Six area reviewers, each working the checklist for its slice of the codebase
(`docs/code-review/`), against the project's defining rule: *a wrong answer is
worse than no answer.* Every finding is ranked on the framework's S1–S4/Nit
scale. `ruff`, `mypy`, and the full `pytest` suite (534 passed / 13 skipped) are
green — as expected; the findings below are what a green suite does **not**
catch.

> Findings are a snapshot of the commit above and are **not** tracked as they
> get fixed — the file records what the first full pass of the framework found,
> not current open state.

## Verdict

The codebase is in strong shape and lives up to its own charter: the injection
invariant holds, the layering/typing promises hold, the Kusto client mirrors the
real SDK faithfully, and the R1–R12 semantic rules are almost entirely honoured
and trap-tested. The review found **1 reproduced S1, 3 S2, 4 S3, 1 S4** — no
class of systemic weakness, but a handful of real divergences and two
un-pinned/untested traps the spec itself lists as open.

## Findings, most-severe first

### S1 — wrong answer

**`extend` that overwrites an existing column moves it to the end.**
`translate/__init__.py:402-408` (and `schema.py:81-85`).
`… | extend a = 99` emits `SELECT COLUMNS(x -> x NOT IN ('a')), 99 AS "a"`, so a
three-column input comes back ordered `['b','c','a']` instead of `['a','b','c']`.
Reproduced at runtime. Kusto's `extend` replaces a column *in place*; column
order is user-visible (TRANSLATION.md §1, §5). Because `schema.py` computes the
same `kept + added` order, a `join` after such an `extend` inherits the wrong
column names/positions too. **Fix the class:** emit the explicit ordered column
list, substituting the new expression at the replaced column's original
position and appending only genuinely-new names; mirror it in
`_operator_columns(Extend)`. Needs an emulator trap test — none exists today.

### S2 — safety / contract

**Negated string operators drop NULL rows.** `functions.py:368/373/378/381/383`.
`!contains` / `!has` / `!startswith` / `!endswith` / `!in` render as a naive
`NOT (…)`. On a NULL column the inner op is NULL, `NOT NULL` is NULL, and the row
is dropped — but Kusto treats a null/absent value as *not containing* the term,
so the negated form is true and the row is **kept**. This is exactly the case
R4 warns "does not always match a naive `NOT (…)`." The registry rows cite only
R3, never R4, and no trap test exercises a NULL left operand. **Fix the whole
`!`-family at once** against the emulator (likely `col IS NULL OR NOT …`), and
cite R4.

**`parse_timespan` leaks `OverflowError` through the public boundary.**
`params.py:344-348`. A `timespan` parameter value of `"1e10"`, `"inf"`, or
`"1e400"` reaches the bare-number fallback `timedelta(days=float(text))`, whose
`except` only catches `ValueError`; the resulting `OverflowError` escapes
`coerce`/`bind` as a raw stdlib exception instead of a clean `KqlSchemaError`.
No SQL is reached and no wrong answer is produced — a robustness/contract defect,
not injection. **Fix:** widen the `except` to `OverflowError` (and reject
non-finite floats) so `parse_timespan` returns `None` → `KqlSchemaError`.

**`sort`/`order` null placement is emitted in the likely-inverted direction —
and is unverified.** `translate/__init__.py:458-461`. Emits `ASC NULLS LAST` /
`DESC NULLS FIRST` (null as the *largest* value); Kusto's docs treat null as the
*smallest*, so ascending should be `NULLS FIRST`. TRANSLATION.md §9 lists this as
an **open item** with no trap test, yet the code commits to a direction and the
comments assert it as fact. **This one needs the emulator to settle** — it
escalates to S1 if the oracle confirms null=smallest. Pin it, add the R6 trap,
set the default.

### S3 — correctness-adjacent

**Wide integers overflow the DataFrame path.** `kusto/_models.py:78-81`,
`helpers.py:46,101`. A `UBIGINT`/`HUGEINT`/`UHUGEINT` value > 2⁶³−1 is labeled
Kusto `long`; `dataframe_from_result_table` then does `.astype(Int64Dtype())` and
raises a raw `OverflowError` (not a `KqlError`/`KustoServiceError` a caller can
catch). Row-level access returns the right int; only the DataFrame path fails.
**Fix the class** (the wide-int→`long` mapping): surface out-of-range values as
`real`/`decimal`/`string`, or have the converter fall back cleanly.

**Scalar `dcount` maps to `approx_count_distinct`, contradicting the aggregate
form and the file's own note.** `functions.py:303` vs `493`. The aggregate row
argues (correctly) that approx is ~13% wrong at corpus cardinalities and even
reorders `top N by dcount`, so it uses exact `count(DISTINCT)`; the scalar row
still emits approx. The scalar row is effectively dead (dcount is only valid in
`summarize`), but it's a landmine for any future path. Remove or align it.

**`_table_columns` case-folds table lookup.** `schema.py:44-47`. It tries
`name`, `name.lower()`, `name.upper()`, so `foo` could bind to a schema entry
`Foo` instead of raising `KqlSchemaError` — the exact "resolve arbitrarily
instead of raising" R7 warns against. Low reachability, but match exactly and
raise on miss.

**`KustoClosedError` is parented on the wrong base.** `kusto/exceptions.py:77`.
Ours inherits `KustoClientError`; the real SDK parents `KustoClosedError` on
`KustoError`. A caller doing `except KustoClientError` (expecting closed-client
errors to propagate, as they do against the SDK) would have ours swallowed.
Reparent to `KustoError`.

### S4 — maintainability

**`needs_schema` has a dead branch and no caller.** `schema.py:31-33`. The second
`if isinstance(op, ir.Join) and needs_schema(op.right)` is unreachable (the prior
line returns for any `Join`), and the function is exported but unused in
`src`/`tests`. *Found independently by two reviewers.* Delete it, or fix it to
recurse into `union`/`in`/`let` subqueries and wire it in.

### Nits

- `kusto/client.py:412` — `USE "{database}"` is the one identifier→SQL path not
  routed through the quote-doubling helper. **Not** a vector (`database` is gated
  by exact-membership against `duckdb_databases()`), but route it through the
  helper for defense-in-depth.
- `kusto/client.py:115` — `with_no_authentication` is not a real
  `KustoConnectionStringBuilder` method (harmless extra, not SDK surface).
- `parser.py:90` — `parse`/`validate`/`to_sql` raise bare `TypeError` on non-`str`
  input; a caller doing `except KqlError` won't catch it. Document in `Raises:`.
- `__init__.py:69` — `TranslationResult`/`Schema`/`Parameters` are used in the
  public `to_sql` signature but aren't in top-level `__all__`, so callers can't
  import them to annotate.
- Doc drift: `ci.yml` runs `ruff check src tools tests`; `CONTRIBUTING.md` writes
  `src tests tools` (same dirs, cosmetic order).

## Two cross-area patterns worth a single fix each

1. **Unhandled `OverflowError` at type boundaries** shows up twice — the timespan
   parameter parser (S2) and the wide-int DataFrame conversion (S3). Same class:
   a stdlib numeric conversion escaping as a raw exception where a typed error
   belongs.
2. **Un-pinned §9 open items reaching users** — the sort null-placement default
   (S2) is committed in code and asserted in comments though the spec lists it as
   unresolved and no trap test exists. The project's own discipline ("a rule is
   not known until its test exists") argues for either a trap test or an explicit
   refusal, not a silent default.

## What was verified clean (high-signal)

- **Injection invariant holds end-to-end.** Values become generated `$kqlp{n}`
  placeholders bound via DuckDB's API; identifiers and literals route through
  single `quote_ident`/`quote_string` doubling helpers; payloads like
  `' | project secret`, `'; DROP TABLE Users; --`, `a" OR "1"="1` were traced
  through `to_sql` and confirmed absent from its output and present as bound
  values. The slot is generated, never derived from the caller's name.
- **Layer 0 stays dependency-light.** `import duckdb_kql` pulls in no
  duckdb/pandas/pyarrow, before or after `to_sql`; `_LAYER1` / `__all__` /
  `TYPE_CHECKING` are mutually consistent; no public signature resolves to an
  undeclared `Any`; the error taxonomy is closed and rooted at `KqlError`.
- **Kusto client mirrors `azure-kusto-python` faithfully** — client/properties/
  response/result shapes match (some byte-for-byte), `OPTION_SUPPORT` agrees with
  its doc table, the wire form and dtype conversions match, and unsupported
  surfaces refuse cleanly via catchable `KustoServiceError(semantic=True)` rather
  than returning silent empty stubs.
- **The oracle can't fabricate.** L3 is frozen-expectation-only and hermetic;
  provenance (emulator + image digest) is enforced; refused cases carry no
  expectation. The comparator distinguishes null/empty/NaN/bool and applies R11
  tolerance only where approximation is real. The recent draft-fixture drift is
  genuinely resolved and baselines are up-only ratchets.
- **R1–R12 largely honoured and trap-tested** — `TRY_CAST` not `CAST`; `has` as
  a term (`\b` regex, not `LIKE '%x%'`); bare `join` as `innerunique`
  (`DISTINCT ON`, verified 2 rows vs 4); default `desc`; UTC everywhere with a
  single `now()`; `dynamic` access that never raises; exact `dcount`; correct
  `summarize` naming; one-operator-one-CTE pipeline; loud refusals for `union`,
  `mv-apply`, `let` functions, and unknown constructs.
