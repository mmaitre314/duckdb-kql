# Build-time translation (`duckdb-kql`)

Translate `.kql` to `.sql` once, in CI. What ships is plain SQL, and **nothing
that runs it needs this package** — not the transpiler, not Python.

```bash
pip install duckdb-kql                      # antlr4 only; no database
duckdb-kql queries/ -o build/sql/           # translate
duckdb-kql queries/ -o build/sql/ --check   # fail the build if stale
```

## Why

The translator is the part with a dependency; its output is not. Translating at
build time means:

- **No runtime dependency.** A Go service, a Rust binary, a `duckdb` CLI script,
  a dbt model and a notebook can all read the same `.sql` file. Only your build
  machine ever installs `duckdb-kql`.
- **Failures move left.** A query that does not translate breaks the build, not
  production. That matters here more than usual: an unsupported construct
  *raises* rather than approximating, so the error you would have seen at
  runtime is the error you now see at build time.
- **Reviewable diffs.** Committing the generated SQL makes a change in
  translation visible in code review, rather than arriving with an upgrade.

## Usage

```
duckdb-kql FILE... [-o PATH] [--check] [--schema FILE] [--no-header] [-v]
```

| | |
|---|---|
| `FILE...` | `.kql` files, or directories (searched recursively). `-` reads stdin. |
| `-o, --output` | A file (with a single input) or a directory. Omit to write to stdout. |
| `--check` | Compare instead of writing; exit 3 if anything is missing or stale. |
| `--schema` | JSON file of `{"Table": ["col", ...]}`. Only `join` needs it. |
| `--no-header` | Emit bare SQL with no comment block. |
| `-v, --verbose` | Report each file written, on stderr. |

```bash
duckdb-kql queries/errors.kql                        # to stdout
duckdb-kql queries/errors.kql -o build/errors.sql    # to one file
duckdb-kql queries/ -o build/                        # a directory of each
echo 'print x = 1' | duckdb-kql -                    # from stdin
```

The command is also `python -m duckdb_kql`, for CI jobs where the console script
is not on `PATH`.

## The generated header

```sql
-- Generated by duckdb-kql from queries/errors.kql. Do not edit.
--
-- Run with TimeZone set to UTC:  SET TimeZone='UTC';
-- KQL datetimes are UTC, and DuckDB reads the session zone when casting
-- text without an offset. Without it, datetimes are silently shifted
-- rather than rejected.

WITH _s0 AS (SELECT * FROM "StormEvents"),
     ...
```

**Set `TimeZone='UTC'` before running the SQL.** `duckdb_kql.kql()` does it for
you at Layer 1; nothing does it for you here. Getting it wrong does not raise —
it shifts every datetime — which is why the warning travels with the file.

The header deliberately contains **no version and no timestamp**. Both would
change the file for reasons unrelated to the query, and a `--check` that fails
after an unrelated upgrade is a check people learn to ignore. Use `--no-header`
if you want the SQL bare.

## Query parameters

Nothing is bound at build time — there are no values yet. A query that declares
parameters produces SQL with placeholders, and the header says which is which:

```kql
declare query_parameters(state:string, since:datetime = datetime(2007-01-01));
StormEvents | where State == state and StartTime > since | count
```

```sql
-- Query parameters. Bind these as VALUES — never by string
-- substitution, which is the whole reason they are placeholders.
--   $kqlp0    state  string, required
--   $kqlp1    since  datetime, default 2007-01-01T00:00:00

WITH _s0 AS (SELECT * FROM "StormEvents"),
     _s1 AS (SELECT * FROM _s0 WHERE (("State" = CAST($kqlp0 AS VARCHAR)) AND ...
```

Bind them by name through whatever DuckDB driver you use:

```python
import duckdb, datetime

con = duckdb.connect("analytics.duckdb")
con.execute("SET TimeZone='UTC'")
sql = open("build/sql/by_state.sql").read()

con.execute(sql, {"kqlp0": user_input, "kqlp1": datetime.datetime(2007, 1, 1)})
```

The slot names are generated, never derived from the KQL name — that is what
keeps caller-supplied text out of the SQL entirely. Defaults are *reported*, not
substituted: a placeholder with a documented default still needs a value.

## Keeping generated SQL honest in CI

Commit the `.sql` and let `--check` prove it matches:

```yaml
- run: pip install duckdb-kql
- run: duckdb-kql queries/ -o sql/ --check
```

An edited `.kql` whose `.sql` was not regenerated fails with exit 3 and a list
of the stale files. This is the same discipline the repository uses for its own
generated files — a generated artifact that can silently drift is worse than no
artifact.

If you would rather not commit the output, translate into the build directory
and skip `--check`:

```yaml
- run: pip install duckdb-kql && duckdb-kql queries/ -o build/sql/
```

Errors are reported as `file:line:column: error: …`, which GitHub Actions and
most editors turn into inline annotations.

## Joins need a schema

`join` is the one operator that has to know the input columns, to reproduce
KQL's column-renaming rules. At Layer 1 the connection supplies them; at build
time there is no connection, so pass a JSON file:

```json
{
  "StormEvents": ["State", "EventType", "StartTime"],
  "PopulationData": ["State", "Population"]
}
```

```bash
duckdb-kql queries/ -o build/sql/ --schema schema.json
```

Everything else translates schema-free. A `join` without a schema fails with a
`KqlSchemaError` rather than guessing at the renaming.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Everything translated. |
| 1 | A query failed to translate (syntax, unsupported construct, missing schema), or a file could not be read. |
| 2 | Bad usage. |
| 3 | `--check` found a missing or out-of-date output. |

1 and 3 are distinct on purpose: "your query is wrong" and "your generated file
is stale" want different reactions, and a CI step should not have to grep the
message to tell them apart.

## Limits

- **One query per file.** KQL's multi-statement form is not supported, so a file
  is one query (plus any `let` and `declare query_parameters`).
- **`--check` compares exact text.** Reformatting the generated SQL by hand will
  fail it. That is the intent: the file is generated.
- **Coverage is the library's coverage.** Anything in
  [the support matrix](kql-support.md)'s "not supported" column fails here too,
  loudly, at build time — which is the better place for it.
